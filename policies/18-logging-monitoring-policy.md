## 1. Purpose

This policy establishes the requirements for logging, monitoring, and alerting across the NextSlide AI presentation generation platform. It defines what events are logged, how personally identifiable information is protected within log data, which monitoring systems are employed, how alerts are configured and escalated, and the retention periods for different log categories. The objective is to maintain sufficient observability for operational troubleshooting, security incident detection, and SOC 2 audit compliance while ensuring that sensitive user data is never exposed in log output.

## 2. Scope

This policy applies to all logging and monitoring activities across the NextSlide platform, including:

- Python backend application logs generated by the FastAPI service via the Python `logging` module.
- Frontend debug logs maintained in the browser's in-memory buffer.
- Error and performance tracking via Sentry for both frontend and backend.
- Product analytics via PostHog.
- Infrastructure monitoring via the Render Dashboard and Supabase Dashboard.
- Audit logs recorded in the `audit_logs` table in Supabase PostgreSQL.
- Health check endpoints and circuit breaker state monitoring.
- All environments: production, staging, and development (with environment-specific configurations).

All personnel who develop, operate, or administer NextSlide systems are subject to this policy.

## 3. Definitions

| Term | Definition |
|---|---|
| **PII** | Personally Identifiable Information; any data that can identify an individual, including email addresses, names, IP addresses, and payment metadata. |
| **PIIRedactionFilter** | A Python logging filter class implemented in NextSlide's logging configuration that applies regex-based redaction of PII patterns before log output is written. |
| **Audit Log** | A structured record of administrative actions stored in the `audit_logs` table in Supabase, providing a tamper-evident trail of privileged operations. |
| **Circuit Breaker** | A fault-tolerance pattern monitoring Supabase connectivity that transitions through CLOSED, OPEN, and HALF_OPEN states based on failure counts and timeout periods. |
| **Health Check** | An HTTP endpoint that returns the operational status of a service or dependency, used for automated monitoring and alerting. |
| **Log Retention** | The defined period for which log data is stored before deletion or archival, varying by log category and compliance requirements. |
| **Trace Sampling** | The percentage of requests for which Sentry collects detailed performance traces, configured to balance observability with overhead. |

## 4. Policy Statements

### 4.1 PII Redaction in Application Logs

All production application logs shall pass through the PIIRedactionFilter before output. The filter applies the following regex-based redaction rules:

- **Email Addresses:** Patterns matching standard email formats are replaced with `[EMAIL_REDACTED]`.
- **Bearer and JWT Tokens:** Authorization headers and JWT strings following `Bearer` or `JWT` prefixes are replaced with `[TOKEN_REDACTED]`.
- **API Keys:** Strings matching patterns `sk-*`, `pk-*`, `ns_live_*`, and `key-*` are replaced with `[KEY_REDACTED]`.
- **Long Base64 Strings:** Base64-encoded strings exceeding a defined length threshold (indicative of tokens or credentials) are replaced with `[TOKEN_REDACTED]`.

The PIIRedactionFilter is mandatory in the production environment. It may be disabled in local development environments for debugging purposes only, provided no real user data is present.

### 4.2 Production Log Configuration

Backend application logging in production follows these configuration requirements:

- **Log Level:** WARNING. Only WARNING, ERROR, and CRITICAL messages are emitted in production. DEBUG and INFO levels are suppressed to reduce log volume and minimize the risk of inadvertent PII exposure.
- **PII Redaction:** Enabled. The PIIRedactionFilter is active on all log handlers.
- **Log Format:** Structured log entries including timestamp, log level, logger name, and message. Stack traces are included for ERROR and CRITICAL levels.
- **Output:** Logs are written to stdout and captured by the Render platform's log aggregation.

Development and staging environments may use lower log levels (DEBUG or INFO) for troubleshooting, but PII redaction shall remain enabled whenever real or realistic user data is present.

### 4.3 Data Explicitly Excluded from Logs

The following categories of data shall never appear in application logs, error reports, or monitoring systems, whether through direct logging or indirect capture:

- **Passwords:** User passwords, password hashes, or password reset tokens in cleartext.
- **Full JWT Tokens:** Complete JSON Web Tokens are redacted; only the token prefix or a truncated reference may appear.
- **Email Addresses:** User email addresses are redacted to `[EMAIL_REDACTED]` by the PIIRedactionFilter.
- **API Keys:** Service API keys (Anthropic, OpenAI, Stripe, Supabase) are redacted to `[KEY_REDACTED]`.
- **Request and Response Bodies:** Full HTTP request and response payloads are not logged, as they may contain user-generated presentation content, file uploads, or payment data.
- **Credit Card Data:** Card numbers, CVVs, expiration dates, or any cardholder data. Stripe handles payment processing, and card data never reaches NextSlide servers.

### 4.4 Sentry Error and Performance Tracking

Sentry is configured for both frontend and backend error and performance monitoring with the following settings:

- **`send_default_pii`:** Set to `false`. Sentry does not automatically collect user IP addresses, cookies, request bodies, or other PII.
- **Trace Sampling Rate:** 10% of requests are sampled for detailed performance traces. This rate balances observability with cost and overhead.
- **Debug Event Filtering:** Debug-level events and non-actionable noise are filtered before transmission to Sentry.
- **Environment Tags:** Events are tagged with the deployment environment (production, staging, development) for filtering.
- **Release Tracking:** Sentry releases are correlated with Render deployment identifiers to associate errors with specific deployments.
- **Alert Rules:** Sentry alerts shall be configured for: new issue types, error rate spikes exceeding baseline thresholds, and performance regressions in critical transaction paths (e.g., deck creation, authentication, AI generation).

### 4.5 Audit Logging

Administrative and privileged actions are recorded in the `audit_logs` table in Supabase PostgreSQL. Each audit log entry contains the following fields:

| Field | Description |
|---|---|
| **action** | The type of administrative action performed (e.g., `user_management`, `credit_adjustment`, `deck_deletion`, `config_change`). |
| **admin_user_id** | The unique identifier of the administrator who performed the action. |
| **target_user_id** | The unique identifier of the user affected by the action, if applicable. |
| **timestamp** | The UTC timestamp when the action was performed. |
| **details** | A structured JSON object containing action-specific context (e.g., credit amount, configuration key changed, reason). |
| **ip_address** | The IP address from which the administrative action was initiated. |

The following events are tracked in the audit log:

- **User Management:** Account creation, suspension, deletion, role changes, and password resets performed by administrators.
- **Credit Adjustments:** Manual additions or deductions of user generation credits by administrators.
- **Deck Deletions:** Administrative deletion of user presentation decks.
- **Configuration Changes:** Modifications to platform configuration settings via the admin interface.
- **All Admin API Calls:** API requests to administrative endpoints that modify system state.

Audit log entries are append-only. Modification or deletion of audit log records is prohibited outside of the data retention schedule. Access to the `audit_logs` table is restricted to authorized administrative personnel through Supabase RLS policies.

### 4.6 Circuit Breaker Monitoring

The Supabase connectivity circuit breaker is monitored for state transitions and operational health:

- **Failure Threshold:** 25 consecutive connection failures trigger the circuit breaker to transition from CLOSED to OPEN state.
- **Open Timeout:** The circuit breaker remains in OPEN state for 30 seconds, during which all Supabase requests are short-circuited with a service unavailable response.
- **State Transitions:** CLOSED (normal operation) to OPEN (failure threshold exceeded) to HALF_OPEN (timeout expired, testing connectivity) to CLOSED (connectivity restored).
- **Logging:** Circuit breaker state transitions (CLOSED to OPEN, OPEN to HALF_OPEN, HALF_OPEN to CLOSED, HALF_OPEN to OPEN) shall be logged at WARNING level or above.
- **Alerting:** Transition to OPEN state shall trigger an alert to the on-call engineer, as it indicates sustained Supabase connectivity failure affecting all database-dependent operations.

### 4.7 Health Check Endpoints

NextSlide maintains the following health check endpoints for automated and manual monitoring:

| Endpoint | Purpose | Expected Behavior |
|---|---|---|
| `GET /api/health` | Basic application health | Returns HTTP 200 if the FastAPI service is running and responsive. |
| `GET /api/health/supabase` | Database connectivity health | Returns HTTP 200 if Supabase PostgreSQL is reachable and responsive. Returns an error status if the circuit breaker is OPEN. |
| `GET /admin/services/health` | Comprehensive service health | Returns health status for all backend dependencies including Supabase, Redis, and external service connectivity. Restricted to administrative access. |

Health check endpoints shall be polled at regular intervals by Render's built-in monitoring or an external uptime monitoring service. Consecutive health check failures shall trigger alerts per the escalation procedure in Section 4.9.

### 4.8 Monitoring Stack

NextSlide employs the following monitoring systems, each serving a distinct function:

| System | Function | Data Collected |
|---|---|---|
| **Sentry** | Error tracking and performance monitoring | Exceptions, stack traces, breadcrumbs, performance traces (10% sampling), release data. PII excluded via `send_default_pii: false`. |
| **PostHog** | Product analytics and user behavior | Feature usage, page views, conversion funnels, user journeys. Used for product decisions, not security monitoring. |
| **Render Dashboard** | Infrastructure monitoring | Deployment status, build logs, service resource utilization (CPU, memory), bandwidth, response times. |
| **Supabase Dashboard** | Database monitoring | Query performance, connection pool utilization, database size, RLS policy evaluation metrics, authentication event logs. |

No single monitoring system provides complete visibility. Security monitoring relies primarily on Sentry (for application-level errors and anomalies), audit logs (for administrative actions), and infrastructure dashboards (for resource and availability metrics).

### 4.9 Alert Configuration and Escalation

Alerts shall be configured with the following severity-based escalation:

- **Critical Alerts (immediate response):** Circuit breaker OPEN state, health check endpoint failures on `/api/health`, Sentry error rate spike exceeding 5x baseline, authentication system failure. Notification: on-call engineer via push notification and email.
- **High Alerts (response within 1 hour):** Supabase health check failure, sustained elevated error rates (2x-5x baseline), deployment build failures on Render. Notification: engineering team via email and chat.
- **Medium Alerts (response within 4 hours):** New Sentry issue types in critical paths (authentication, payment, AI generation), resource utilization exceeding 80% on Render services. Notification: engineering team via email.
- **Low Alerts (next business day):** Non-critical Sentry issues, PostHog anomaly flags, dependency vulnerability notifications. Notification: engineering team via email digest.

Alert fatigue shall be mitigated through regular tuning of alert thresholds, suppression of known non-actionable alerts, and periodic review of alert effectiveness.

### 4.10 Log Retention

Log data shall be retained according to the following schedule:

| Log Category | Retention Period | Storage Location |
|---|---|---|
| **Sentry Events** | 90 days | Sentry cloud (managed retention) |
| **Render Application Logs** | Per Render plan limits | Render platform |
| **Audit Logs** | Indefinite | Supabase PostgreSQL `audit_logs` table |
| **Frontend Debug Logs** | Session only (in-memory, max 100 entries) | Browser memory; not persisted |
| **PostHog Analytics** | Per PostHog plan limits | PostHog cloud |

Audit logs are retained indefinitely to support compliance, forensic investigation, and historical audit requirements. Audit log storage shall be monitored for capacity and the retention policy reviewed annually. Frontend debug logs are stored in an in-memory circular buffer limited to 100 entries and are cleared when the browser session ends; they are never transmitted to external systems.

### 4.11 Frontend Debug Logging

The frontend application maintains a limited in-memory debug log for development and troubleshooting:

- **Storage:** In-memory circular buffer within the browser, not persisted to disk or transmitted externally.
- **Capacity:** Maximum 100 entries. Oldest entries are evicted when the buffer is full.
- **Content:** Application state transitions, API request metadata (method, URL, status code -- not request/response bodies), and rendering lifecycle events.
- **Access:** Available only through browser developer tools during an active session. Not accessible to server-side systems or third parties.
- **PII:** Frontend debug logs shall not intentionally capture user email addresses, passwords, tokens, or presentation content. Component-level logging should reference entity IDs rather than user-identifiable data.

## 7. Compliance and Enforcement

All personnel are required to comply with this policy. Violations include but are not limited to: disabling or circumventing PII redaction filters in production, logging prohibited data categories (passwords, credit card data, full JWT tokens), modifying or deleting audit log records, disabling health check endpoints, or ignoring Critical and High severity alerts without documented justification. Violations may result in disciplinary action up to and including termination of employment or contract.

## 8. Exceptions

Exceptions to this policy must be requested in writing to the CTO, include a justification and risk assessment, and specify compensating controls. Exceptions to PII redaction requirements require both CTO and CEO approval due to privacy and compliance implications. Temporary elevation of production log levels to DEBUG or INFO for incident troubleshooting is permitted for a maximum of 4 hours with CTO authorization, provided PII redaction remains enabled. All exceptions are documented and time-limited to 90 days.

## 9. Review Schedule

This policy shall be reviewed:

- Annually, on or before the Next Review Date listed in the document header.
- Upon changes to the monitoring stack (addition, removal, or replacement of Sentry, PostHog, Render, or Supabase monitoring capabilities).
- Following any incident where inadequate logging, missed alerts, or PII exposure in logs was a contributing factor.
- Upon changes to privacy regulations or SOC 2 requirements affecting log data handling.
- After audit findings related to logging, monitoring, or data retention.
